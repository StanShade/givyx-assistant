# SEO + GEO checklist (Generative Engine Optimization)

> **When to read:** before publishing an article that targets search traffic. The canonical source of every check in Stage 13 (SEO/GEO audit on prod). Keep the specific thresholds and paths here, so they can change without editing the methodology.
>
> **Why:** optimise at the same time for classic search (Google, Bing and others) and for citation by language models (Perplexity, ChatGPT browse, Claude web search, Gemini, AI Overviews). These are two disciplines, but ~80% of the work overlaps.
>
> **Main principle:** this file is the single source of truth for SEO+GEO checks. Before publishing, the agent runs through sections 1-9 top to bottom. Each section = one or more checkable items. Whatever your CMS serves (structured data, sitemap, registries for language models) is encapsulated behind `cms.adapter`; the registry paths live in `config.*`.

---

## 1. Machine-readable site registries (the base)

Before adding anything new - know what your CMS already serves. These are generic mechanisms supported by any engine:

| Artifact | What it does |
|---|---|
| `sitemap.xml` | Sitemap with priorities by article type (pillar = 1.0, how-to = 0.8). A new article lands there automatically if the CMS pulls in everything published. |
| `robots.txt` | Search-engine and language-model bots are explicitly allowed (crawlers of the major search engines + AI assistants). Block only what genuinely should not end up in datasets. |
| Structured data (JSON-LD) | Graph of `Article` + `Person` + `WebPage` + `BreadcrumbList` (+ `HowTo` for how-tos, `FAQPage` for Q&A blocks, `VideoObject` if there is video). Generated by `cms.adapter`. |
| Registry for language models (if the CMS serves it) | Text index/dump of the articles per the `llmstxt.org` standard. Path - in `config.*`. See section 8: this is an auxiliary signal, not the main one. |
| Markdown version of pages (if the CMS serves it) | Clean Markdown with no HTML wrapper for language-model crawlers. The main GEO practice that actually works - see section 8. |

**What is critical to use as-is:** the registries are assembled from CMS data - a new article lands in them by itself. Do not rebuild them by hand.

## 2. GEO citability patterns (9 rules) - for language models

These are structural rules by which an AI assistant **pulls a passage out as a quote**. Written in this format - it lands in Answer Boxes; not written this way - it does not.

⚠️ **Editorial standard v3 amendment:** these are working heuristics, not a proven guarantee of citation. Do not spoil live text for the sake of formal quotas: "50% of H2s as questions" is a guideline, not a requirement; if a question in an H2 sounds forced, write an affirmative answer-headline. When a GEO quota conflicts with clarity for a human, the human wins.

### 2.1. Answer-first paragraph of 40-75 words at the start of every H2

The first paragraph of every section must **answer the H2 question straight away**, without three paragraphs of run-up. A short, precise answer, like an encyclopedia entry.

**Rule:** 40-75 words, exactly one statement, no framing. Count the words in the first block of every H2 (the generic summary block / TL;DR).

### 2.2. Question-based H2 headings

"How do you set up X?", "Why do you need Y?", "What is Z?" - not "Setting up X", "Y", "Definition of Z". Up to 10 words. **At least 50% of H2s in question form** (or as an affirmative answer to a question).

### 2.3. Standalone sections

Every H2 + its content must work **without reading the neighbouring sections**. The model quotes a chunk out of the context of its neighbours.

```bash
grep -niE '(as we saw above|as mentioned above|as noted above|below we will look at|as discussed earlier|continuing the topic|in the previous section|in the next section)' <path>
```

Every hit - rewrite into standalone wording.

### 2.4. Paragraph = 2-4 sentences, one idea

The model cuts long paragraphs in the middle -> distorts the meaning. Short ones are quoted whole. Count the average number of sentences per paragraph; >4 - split.

### 2.5. Comparisons = tables, not running text

Language models cite tables noticeably more often than prose (by industry measurements - several times more). Any "A vs B" comparison - format as a table `| Feature | A | B |`. Constructions like "A is better because..., B is better because..." - reformat. At least 1 comparison table per article.

### 2.6. Processes = numbered lists

"Do X, then Y, then Z" - a **numbered** list (`1. 2. 3.`), not bullets (`- - -`). Numbered lists get a noticeable citation boost. Bullets - only for unordered enumerations (features, attributes).

### 2.7. Fact-dense sentences with named sources

"According to [X](url)...", "<Source> reports that..." - specific numbers, dates, source names. Not "rumour has it", "as many say", "apparently". Every number has a link or was verified by the fact-checker. Quotes - with attribution (author + source).

### 2.8. Explicit naming of entities

"<Entity> did X", not "it did X". Language models lose anaphora after 2-3 paragraphs. Do not use "it/this/he/she" further than 2 sentences from the first mention - better to repeat the name.

### 2.9. Clean semantic HTML

Real `<h1>`, `<h2>`, `<ol>`, `<table>` - not styled `<div>`s. If your engine renders structure through semantic tags - make sure the parser does not swap them for presentational ones.

## 3. Schema.org JSON-LD (best practices)

> If `cms.adapter` does not generate structured data - close the whole section as `[x] SKIP: CMS does not generate schema`.

### 3.1. Which types to keep

| Type | Where |
|---|---|
| `Article` | main |
| `Person` (author + reviewer, if any) | author / reviewedBy |
| `WebPage` + `mainEntityOfPage` | mainEntityOfPage |
| `HowTo` + `HowToStep` | for how-tos |
| `FAQPage` + `Question` + `Answer` | for Q&A blocks |
| `VideoObject` | if there is video |
| `BreadcrumbList` | navigation |
| `Organization` | publisher |

⚠️ **Licensed/regulated types are banned.** If your niche has formats that by law only a holder of a licence/certificate may use - the matching markup types are banned too (keep them in `editorial.banned_words`, the check is in `checklists/compliance.md`). Only neutral types may remain.

### 3.2. E-E-A-T through `Person` - what is mandatory

The main authority signal. On the `Person` object:

```json
{
  "@type": "Person",
  "name": "<author name, no job titles in the string>",
  "url": "<author page>",
  "jobTitle": "<job title as a separate field>",
  "knowsAbout": ["<expertise topic 1>", "<topic 2>", "<topic 3>"],
  "sameAs": ["<public profile 1>", "<profile 2>", "<profile 3>"]
}
```

**What to check:**
- `Person.name` - name only (no job titles or prefixes like "Dr.", "Senior Engineer").
- `jobTitle` - as a separate field.
- `knowsAbout` - an array of expertise tags (topical authority).
- `sameAs` - an array of URLs to the author's public accounts (social networks, video platforms, profiles). **At least 3.** This is the main E-E-A-T signal.

### 3.3. What search engines require

- `author.name` - name only, no prefixes.
- Multiple authors - each as a separate array element, not a comma-separated string.
- ISO 8601 for dates **with timezone**: `2026-05-18T10:00:00+02:00`.
- Update `dateModified` on **every edit** - a freshness signal.

### 3.4. FAQPage - rich results were pulled, but AI cites it

Some search engines removed FAQ rich results, but AI Overviews cite pages with `FAQPage` schema noticeably more often. **Keep it as-is.** Do not leave `FAQPage` without `dateModified` - the model parses it even without a rich result. The markup must match the visible content: do not add FAQ/HowTo/ratings for the promise of a rich snippet, and do not present the presence of JSON-LD as a ranking gain (standard v3).

### 3.5. Validation

```bash
# Compile-time typing (if the stack is TypeScript): add the Schema.org types package.
# Runtime validation before publishing - with a public structured-data validator:
#   run the article URL through the Schema.org validator and the Rich Results Test.
```

Check: all types valid, no warnings about required fields (`datePublished`, `dateModified`, `headline`, `image`).

## 4. Freshness and evergreen-content signals

### 4.1. Year in title/H1 - only if the year changes the answer

The "<topic> in <current year>" construction works for citability **only when currency genuinely changes the answer** (pricing, versions, availability). Standard v3: do not stamp the year mechanically into every evergreen article and do not bump the date without a real content review - the search engine can tell freshness from cosmetics.

### 4.2. Update `dateModified` on edits

On every edit - update the article's modification date (many CMSs do it automatically). It goes into `dateModified` in the JSON-LD.

### 4.3. Regular review of pillar articles

Review evergreen articles (pillars, how-tos with a year suffix) **every 60-90 days**. At minimum - update the last-reviewed date and add an entry to the changelog inside the article. If your CMS has an auto-reminder for staleness (>90 days without an update) - use it.

## 5. Notifying search engines about indexing

### 5.1. Instant ping (the main channel for some search engines)

- The instant indexing-notification mechanism is IndexNow: an industry standard supported by the major search engines - Bing, Yandex, Naver, Seznam (except one large engine, Google - it indexes through its normal crawl).
- The submit is done by `cms.adapter` after publication, or by you (the owner) manually through the webmaster console.
- Check that the ping went to **several** supporting engines, not just one (an IndexNow submission is shared between participating engines).
- If the mechanism requires a public key file - make sure it is available at the declared address.

### 5.2. Webmaster consoles

Sitemap submit - automatic (Google Search Console, Bing Webmaster Tools, Yandex Webmaster if you serve that market). Once a week you can pull the top queries through the console API for "which phrases the article was found by" analytics.

### 5.3. The search engine without an instant ping

Google: submit the sitemap in Search Console (done once). Indexing - through the normal crawl (hours to days). Check that the article appeared in `sitemap.xml` (it is pulled in automatically from what is published) and that the page cache was purged (on-demand revalidation / CDN purge by path).

## 6. Core Web Vitals and performance

### 6.1. Budgets (at p75 of real users, mobile)

| Metric | Target | What it means |
|---|---|---|
| **LCP** | < 2.5s | Largest Contentful Paint - the largest visible element |
| **INP** | < 200ms | Interaction to Next Paint - responsiveness to an action |
| **CLS** | < 0.1 | Cumulative Layout Shift - how much the layout jumps |

A significant share of sites fail specifically on INP - the most common problem (long JavaScript tasks on the client).

### 6.2. Lab budgets (in pre-deploy via any Lighthouse-compatible run)

| Metric | Target |
|---|---|
| Performance score | ≥ 90 |
| Accessibility | ≥ 95 |
| SEO | = 100 |
| Best Practices | ≥ 90 |
| FCP | < 1.8s |
| TBT | < 200ms (proxy for INP) |

### 6.3. How to measure

- **CI option:** a Lighthouse run in pre-deploy with a budget file, block the merge when the budget fails.
- **Quick option:** a manual run of a public speed tester (PageSpeed Insights and equivalents - the industry standard) for mobile and desktop separately.

Typical causes of failure:
- LCP - a heavy unoptimised cover image, no lazy-load on images below the fold, fonts blocking render.
- INP - long JS tasks on the client.
- CLS - images without set width/height, dynamic banners that "jump".

## 8. Markdown alternative pages (the main GEO gap)

Market leaders serve a `.md` version of every page for language-model crawlers. This is **the GEO practice that works best** - more important than the registry for language models itself.

### 8.1. How it works

The crawler requests the page with `Accept: text/markdown` OR the `.md` suffix. The server returns **clean Markdown with no HTML wrapper**, navigation, widgets or footers. The model gets the content without noise.

### 8.2. Check

```bash
# If the CMS can serve a markdown version - it works:
curl -s -H "Accept: text/markdown" https://<config.project.domain><config.project.content_path>/<slug>
# Expect clean markdown, not HTML.
```

Implementation belongs to `cms.adapter` (a route handler detecting `Accept` / crawler UAs + a `/<slug>.md` redirect). The registry for language models (section 1) is an auxiliary signal, overhyped relative to its real effect: do the minimum, do not invest in it as the main channel. The Markdown export matters more.

## 9. Full pre-publish gate (SEO+GEO)

Before publishing to prod - every item:

### Content (GEO structure)
- [ ] H1 contains `target_keyword` (+ the current year, only if the year changes the answer)
- [ ] H2 headings are clear without the body; question form - where natural, no quota
- [ ] Summary block (TL;DR) of 40-75 words at the start of every H2
- [ ] Paragraphs of 2-4 sentences, one idea each
- [ ] Standalone sections (no "as we saw above")
- [ ] At least 1 comparison table
- [ ] Processes - **numbered** lists
- [ ] Every number has a link to a source
- [ ] Explicit naming of entities (no "it/this" 2+ sentences later)

### Schema.org / E-E-A-T (or SKIP if the CMS does not generate it)
- [ ] JSON-LD validates (public validator / Rich Results Test)
- [ ] `Article` + `Person` + `Organization` + `BreadcrumbList` are present
- [ ] `Person.knowsAbout` is filled in
- [ ] `Person.sameAs` includes 3+ public profiles of the author
- [ ] No licensed/banned types from `editorial.banned_words`

### Technical SEO
- [ ] Lighthouse mobile: Performance ≥ 90, SEO = 100, A11y ≥ 95
- [ ] LCP < 2.5s, INP < 200ms, CLS < 0.1 at p75
- [ ] `meta_title` ≤ 70 characters
- [ ] `meta_description` 100-160 characters
- [ ] OG image generated and working (if `config.image.tool` is set)
- [ ] Canonical URL set

### Indexing
- [ ] Article in `sitemap.xml` (curl test: `grep <slug>`)
- [ ] Article in the registry for language models, if the CMS serves it (curl test)
- [ ] Markdown version served, if the CMS can (curl with `Accept: text/markdown`)
- [ ] IndexNow ping went to several supporting search engines (Bing/Yandex/Naver/Seznam); Google - sitemap in Search Console
- [ ] Page cache purged (revalidate by path)

### GEO check as a bot
- [ ] Content is visible directly in the HTML (not loaded by JS) - check with `curl -A "<bot-UA>"`
- [ ] Structured data is readable (`application/ld+json` in the HTML)
- [ ] No `noindex` / `nofollow`
- [ ] HTTP 200 for the bot, not 403 (bot protection does not cut off useful crawlers)

### Freshness and cluster
- [ ] `dateModified` updated
- [ ] Article attached to 1-3 categories (Stage 9a)
- [ ] Internal links to 3+ other articles in your `content_path`
- [ ] If there is a pillar article - `parent_slug` is set

## 10. What NOT to do (anti-practices)

- Do not invest in the registry for language models as the main signal - right now it is decorative (a trickle of hits against total AI-bot traffic). Do the minimum.
- Do not leave `FAQPage` schema without `dateModified` - AI parses it even when the rich result is gone.
- Do not serve language-model crawlers HTML with navigation/footer/widgets - it is noise.
- Do not allow scraper crawlers that send no referral traffic if the content is not wanted in their datasets.
- Do not publish low-quality articles daily - helpful-content algorithms punish churn.
- Do not use running text for comparisons - format as a table.
- Do not split one idea across 7 paragraphs - collect it into one of 2-4 sentences or into a table.
